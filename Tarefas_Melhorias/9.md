MERCADO PAGO

O Mercado Pago é a única autoridade para determinar confirmação do pagamento.

Nunca considere pagamento aprovado com base:

* em query string;
* URL de retorno;
* estado enviado pelo frontend;
* localStorage;
* sessionStorage.

Criar ou revisar:

POST /api/webhooks/mercado-pago

O endpoint deverá:

1. receber a notificação;
2. validar a autenticidade usando o mecanismo oficialmente documentado;
3. consultar/confirmar o recurso correspondente no Mercado Pago quando necessário;
4. localizar o pedido usando identificadores internos/external_reference;
5. atualizar o pagamento de maneira transacional/idempotente;
6. nunca processar duas vezes o mesmo pagamento;
7. criar um integration job para Bling somente após estado confirmado como aprovado;
8. responder rapidamente ao webhook;
9. mover trabalho pesado para processamento assíncrono quando apropriado.

Estados internos de pagamento devem ser claramente modelados.

Exemplos conceituais:

pending
approved
rejected
cancelled
refunded
partially_refunded

Não sobrescreva informação válida com eventos antigos.

BLING WEBHOOK

Criar:

POST /api/webhooks/bling

O endpoint precisa:

1. obter o RAW BODY antes de qualquer modificação;
2. ler X-Bling-Signature-256;
3. calcular HMAC SHA-256 usando o Client Secret;
4. comparar assinatura usando comparação timing-safe;
5. rejeitar assinatura inválida;
6. persistir identificador do evento;
7. ser idempotente;
8. responder 2xx rapidamente quando o evento tiver sido aceito;
9. processar trabalho pesado de modo assíncrono quando adequado.

Considere que:

* webhooks podem ser repetidos;
* não há garantia de ordem;
* uma atualização pode chegar antes de outro evento relacionado.

Criar processamento capaz de reconciliar o estado consultando a API quando necessário.

Eventos relevantes:

* pedidos;
* produtos;
* estoque;
* notas fiscais.

Nunca confiar cegamente nos dados de um webhook para substituir um estado mais recente.
