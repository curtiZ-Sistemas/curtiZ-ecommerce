# 1. REGRA PRINCIPAL DE CONTAS

Esta regra é obrigatória.

TODO usuário que fizer cadastro pela loja curti Z deverá inicialmente receber acesso de:

CLIENTE.

Não existe cadastro público diretamente como:

* administrador;
* operador;
* gerencial;
* técnico.

Cadastro público significa:

usuário autenticado + perfil + acesso de cliente.

Essa atribuição deverá acontecer de maneira segura no backend/banco.

Nunca confiar em:

role enviado pelo frontend;
query parameter;
localStorage;
cookie manipulável;
body da requisição.

O navegador nunca poderá dizer:

"quero me cadastrar como administrador".

Mesmo que alguém modifique manualmente a requisição.

---

# 2. CLIENTE COMO ACESSO PADRÃO

Depois do cadastro:

usuário -> cliente

O sistema deverá garantir isso automaticamente.

Se existir trigger/função segura no banco atualmente responsável pela criação do profile, analisar e adaptar a estrutura existente.

Preferencialmente essa regra deve ser protegida no banco e/ou backend, e não depender apenas do React.

Criar testes garantindo que:

cadastro normal -> cliente

cadastro manipulando role=admin -> cliente

cadastro manipulando role=technical -> cliente

cadastro manipulando role=manager -> cliente

cadastro manipulando role=operator -> cliente

Nunca permitir privilege escalation pelo cadastro.

---

# 3. NOVO MODELO DE GERENCIAMENTO DE ACESSOS

Quero regras extremamente claras.

Os acessos relevantes serão:

* client;
* admin;
* operator;
* manager;
* technical;

respeitando os nomes reais dos enums/roles existentes no projeto.

Não renomear enums existentes sem necessidade.

Se atualmente os nomes forem diferentes, adaptar estas regras à estrutura existente.

---

# 4. O QUE O GERENCIAL PODE GERENCIAR

Somente usuários com acesso GERENCIAL podem gerenciar pela interface os seguintes acessos:

CLIENTE

ADMINISTRADOR

OPERADOR

O gerencial poderá, para outro usuário:

* adicionar acesso de cliente;
* remover acesso de cliente;
* adicionar acesso de administrador;
* remover acesso de administrador;
* adicionar acesso de operador;
* remover acesso de operador.

Também poderá existir:

Administrador + Operador

simultaneamente.

Portanto o sistema deverá suportar múltiplos acessos por usuário.

Exemplo:

Usuário A:
Cliente

Usuário B:
Administrador

Usuário C:
Operador

Usuário D:
Administrador + Operador

Usuário E:
Cliente + Administrador

se essa combinação for deliberadamente escolhida.

Não transformar role em um único campo que impossibilite múltiplos acessos caso a arquitetura atual já suporte RBAC multi-role.

---

# 5. CLIENTE PODE SER REMOVIDO

Apesar de todo cadastro começar obrigatoriamente como cliente, posteriormente um GERENCIAL poderá remover esse acesso.

Exemplo:

João faz cadastro.

Inicialmente:

Cliente

Depois o gerencial poderá transformar para:

Administrador

ou:

Operador

ou:

Administrador + Operador

e remover Cliente.

Também poderá, se desejar, manter:

Cliente + Administrador

ou outras combinações permitidas.

Portanto:

"todo cadastro começa como cliente"

não significa:

"todo usuário será cliente para sempre".

---

# 6. NÃO DEIXAR USUÁRIO ACIDENTALMENTE SEM ACESSO

Na tela de edição de acessos:

se a remoção resultar no usuário sem nenhum acesso utilizável, impedir a operação acidental ou exigir uma ação administrativa específica existente para desabilitar conta.

Não deixar uma simples desmarcação produzir usuários órfãos ou estados inconsistentes.

Se o sistema atual já tiver status:

active;
disabled;
blocked;

respeitar essa arquitetura.

Não criar uma segunda forma conflitante de desativar conta.

# 7. GERENCIAL NÃO PODERÁ SER ATRIBUÍDO PELA INTERFACE

Esta regra é absoluta.

NÃO criar botão:

"Tornar gerencial"

NÃO criar checkbox:

"Gerencial"

NÃO colocar Gerencial dentro do seletor comum de acessos.

NÃO permitir pela API pública/interna normal utilizada pela interface.

Os usuários GERENCIAIS atualmente existentes continuam gerenciais.

Se futuramente for necessário criar outro gerencial:

isso será feito MANUALMENTE no banco de dados por pessoa autorizada.

A interface não deve permitir criar novos gerenciais.

---

# 8. GERENCIAL NÃO DEVE SER REMOVIDO PELA INTERFACE

Pelo mesmo princípio:

a interface normal também não deverá permitir remover o acesso gerencial.

Gerenciamento de GERENCIAIS permanecerá fora do fluxo normal.

Alterações deste nível serão feitas manualmente no banco por pessoa autorizada.

Isso evita que um erro de interface ou operador elimine os únicos acessos gerenciais.

---

# 9. ACESSO TÉCNICO

Usuários que já possuem acesso TÉCNICO poderão conceder acesso TÉCNICO a outro usuário.

Portanto:

Técnico -> pode adicionar Technical.

Também deverá ser possível remover acesso técnico através da área técnica apropriada por um usuário técnico autorizado, desde que isso não quebre regras críticas do sistema.

Não misturar esse gerenciamento com os acessos administrativos comuns.

---

# 10. TÉCNICO NÃO CRIA GERENCIAL

Técnico NÃO pode através da interface conceder:

Manager/Gerencial.

Essa função continua exclusivamente manual no banco.

---

# 11. TÉCNICO NÃO GANHA AUTOMATICAMENTE OUTRAS PERMISSÕES

O fato de poder gerenciar acesso técnico não significa automaticamente que Technical poderá conceder:

Admin;
Operator;
Client;

a menos que esse mesmo usuário também possua Manager.

A autorização é baseada nos acessos reais da pessoa.

Exemplo:

Usuário possui somente Technical:

pode gerenciar Technical conforme permitido.

Usuário possui:

Technical + Manager

então poderá realizar as ações permitidas por ambas as funções.

Não criar exceções inseguras no frontend.

# 120. REGRA FINAL DE ACESSOS — NÃO INTERPRETAR DIFERENTE

Para evitar ambiguidades, esta é a regra final:

Client.

MANAGER/GERENCIAL:

pode adicionar/remover Client.

pode adicionar/remover Admin.

pode adicionar/remover Operator.

pode conceder Admin + Operator simultaneamente.

pode remover Client e deixar Admin, Operator ou Admin + Operator.

NÃO pode criar Manager pela interface.

NÃO pode remover Manager pela interface.

MANAGER continuará sendo gerenciado somente manualmente no banco.

TECHNICAL/TÉCNICO:

pode adicionar Technical.

pode remover Technical quando permitido pela política implementada.

NÃO pode criar Manager.

NÃO recebe automaticamente direito de gerenciar Admin/Operator/Client.

Se a mesma pessoa possuir:

Manager + Technical

ela possui a união das duas permissões.

ADMIN:

não recebe direito de gerenciar funções apenas por ser Admin.

OPERATOR:

não recebe direito de gerenciar funções.

CLIENT:

não recebe direito de gerenciar funções.

PUBLIC/ANON:

não escolhe função.

Cadastro público sempre recebe apenas Client inicialmente.

Estas regras devem ser aplicadas:

na UI;
no backend;
no banco;
nas RPCs;
nas RLS policies;
nos testes;
na auditoria.

Não aceitar nenhuma implementação em que esconder botões seja a única proteção.
