# 2. INVESTIGAR ERRO 1102

Procure padrões que possam causar excesso de CPU ou memória:

* loops grandes;
* loops aninhados;
* `.map().filter().reduce()` repetidos sobre grandes arrays;
* ordenações grandes no JavaScript;
* serialização JSON repetida;
* `JSON.stringify` de objetos grandes;
* parsing repetido;
* regex pesada;
* processamento de imagens no Worker;
* transformação de dados que deveria ocorrer no banco;
* consultas retornando dados demais;
* N+1 queries;
* requests duplicados;
* renderização SSR excessivamente pesada;
* código executado em toda requisição;
* trabalho pesado no escopo global;
* importações muito grandes;
* objetos globais gigantes;
* respostas inteiras carregadas em memória;
* múltiplas cópias de grandes arrays/objetos.

Corrija somente problemas comprovados ou claramente ineficientes.

# 4. SUPABASE DEVE FAZER O TRABALHO CERTO

Não buscar milhares de registros para depois filtrar no Worker.

Sempre que adequado, faça:

```text
Supabase/Postgres
    ↓
filtrar
ordenar
paginar
agregar
    ↓
Worker recebe somente resultado necessário
```

e NÃO:

```text
Supabase
    ↓
retorna tabela enorme
    ↓
Worker filtra tudo em JavaScript
```

Use queries/RPCs existentes corretamente.

---

# 5. PAGINAÇÃO

Toda listagem potencialmente grande deve possuir limite.

Exemplos:

* produtos;
* pedidos;
* clientes;
* representantes;
* chamados;
* auditoria;
* busca;
* recomendações.

Não carregar centenas/milhares de itens sem necessidade.

Use paginação ou cursor conforme arquitetura atual.

---

# 6. SELECT DO SUPABASE

Evite:

```text
select("*")
```

quando a página utiliza apenas poucos campos.

Busque somente dados realmente necessários.

Exemplo conceitual:

em cards de produto, não buscar descrição completa, SEO, histórico e campos administrativos se só forem necessários:

* id;
* slug;
* nome;
* preço;
* imagem;
* disponibilidade.

Adapte ao schema real.

---

# 7. N+1 QUERIES

Procure situações semelhantes a:

```text
buscar produtos

para cada produto:
    buscar imagem
    buscar estoque
    buscar variante
```

Evite.

Prefira:

* joins adequados;
* RPC existente;
* queries agregadas;
* batch.

Não executar dezenas de chamadas ao Supabase para construir uma única página.

---

# 8. PARALELISMO

Quando operações independentes precisarem acontecer na mesma request:

evite:

```ts
await A();
await B();
await C();
```

quando B e C não dependem de A.

Use paralelismo controlado:

```ts
await Promise.all([
  A(),
  B(),
  C()
]);
```

somente quando seguro.

Não criar dezenas de requests simultâneas.

---

# 11. REVALIDAÇÃO

Quando possível, prefira revalidação controlada para conteúdo público que não muda a cada segundo.

Evite recalcular toda a página em toda request se os dados puderem ser reutilizados de forma segura.

# 12. SSR

Analise páginas que estão fazendo SSR desnecessariamente pesado.

Não transforme tudo em client-side apenas para reduzir Worker CPU.

* cache/revalidation;

# 13. SERVER COMPONENTS

Revise Server Components para evitar:

* transformação pesada repetida;

Reutilize/deduplique quando apropriado.

* `generateMetadata`;
* JSON-LD;
* Open Graph;

# 15. RECOMENDAÇÕES

As recomendações adicionadas a:

* carrinho;
* páginas de erro;
* produto;

Não criar algoritmo pesado dentro do Worker.

Exemplo:

```text

```

---

# 16. BUSCA

A busca não deve trazer catálogo inteiro para memória.

Use query server-side limitada.

Implementar:

* limite;
* paginação;
* debounce client-side;
* sanitização.

Evite algoritmos de fuzzy search pesados executados em grandes arrays dentro do Worker.

---

# 17. CARRINHO

O carrinho não deve executar sincronizações repetitivas.

Verifique:

* `/api/cart/sync`;
* effects;
* atualizações de quantidade;
* reload;
* login.

Evite chamadas duplicadas ou loops como:

```text
render
→ sync
→ state update
→ render
→ sync
```

Sincronizar somente quando necessário.

---

# 18. CHECKOUT

Evite recalcular/processar informações pesadas várias vezes na mesma request.

Preço e estoque precisam continuar sendo validados server-side, mas faça isso de forma eficiente.

Prefira batch query para todas as variantes do carrinho em vez de uma query individual por item.

---

# 20. AUDITORIA

# 21. PROCESSAMENTO NO ESCOPO GLOBAL

Revise código executado fora dos handlers/componentes.

Não executar no startup do Worker:

* processamento pesado;
* geração de arrays enormes;
* parsing grande;
* inicializações caras;
* operações repetidas.

---

# 22. MEMÓRIA

Evite manter grandes estruturas em memória.

Procure:

* arrays gigantes;
* cópias de arrays;
* spreads repetidos em grandes coleções;
* concatenação enorme;
* buffers;
* blobs;
* `arrayBuffer()` desnecessários;
* responses grandes sendo totalmente lidas antes de responder.

---

# 23. STREAMING

Quando existir resposta realmente grande, não bufferizar tudo sem necessidade.

Utilize streaming somente onde fizer sentido e for compatível com Next.js/OpenNext.

Não faça mudança complexa apenas para "usar streaming".

---

# 24. IMAGENS

O Worker NÃO deve fazer processamento pesado de imagem manualmente.

Não:

* redimensionar imagem via JS dentro da request;
* converter grandes buffers;
* baixar imagem inteira para reprocessar no Worker.

Use infraestrutura existente de imagens/CDN/Next Image.

---

# 26. MIDDLEWARE

* consultas pesadas;

# 35. TRATAMENTO DO 1102

Não tente capturar "Error 1102" dentro da própria aplicação como principal solução.

Quando o limite do Worker é excedido, a execução pode ser encerrada pela plataforma.

A solução deve ser reduzir o uso de recursos antes disso acontecer.

# 38. SUBREQUESTS

# 39. TIMEOUT/FAILURE
