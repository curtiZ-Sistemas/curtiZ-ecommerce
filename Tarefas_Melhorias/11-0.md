# 1. REGRA PRINCIPAL DE PERFORMANCE

Não quero um sistema onde cada clique faça uma consulta pesada ao banco.

A arquitetura deve priorizar:

* Edge computing;
* processamento assíncrono;
* cache;
* agregação;
* batch de eventos;
* índices adequados;
* consultas pequenas;
* payloads pequenos;
* algoritmos O(1), O(log n) ou consultas pré-computadas sempre que possível;
* nenhuma consulta N+1;
* nenhum cálculo pesado no navegador;
* nenhum ranking global recalculado para cada visitante.

A aplicação deve continuar extremamente rápida mesmo com milhares de sessões concorrentes.

Não prometa “0 ms”.

Implemente metas realistas e mensuráveis.

Objetivos iniciais:

* respostas provenientes de Edge Cache: preferencialmente < 50 ms;
* recomendação cacheada: preferencialmente < 100 ms;
* recomendação que precise consultar backend: p95 preferencialmente < 250 ms;
* tracking comportamental não pode bloquear navegação;
* interação do cliente deve continuar responsiva mesmo quando analytics/recomendação estiverem indisponíveis.

Esses números são metas de engenharia, não motivo para criar atalhos inseguros.

# 2. PRINCÍPIO FUNDAMENTAL

O sistema NÃO deve tentar descobrir a identidade real de visitantes anônimos.

Deve identificar:

**intenção de compra da sessão**

e não características pessoais sensíveis.

Não implementar:

* fingerprinting agressivo;
* rastreamento invasivo;
* inferência de religião;
* raça;
* saúde;
* sexualidade;
* opiniões políticas;
* outros dados sensíveis.

Utilizar identificador anônimo de sessão/visitante conforme necessário.

Se o usuário entrar na conta, poderá haver associação segura entre histórico permitido e conta, respeitando as regras de privacidade existentes.

Preparar tudo de maneira compatível com boas práticas de LGPD:

* minimização;
* finalidade;
* retenção;
* transparência;
* consentimento quando necessário;
* possibilidade de exclusão;
* possibilidade de desativar personalização.

# 4. INGESTÃO DE EVENTOS SEM PESAR O SITE

Não fazer:

`ação do usuário → INSERT Supabase → aguardar → continuar UI`

O tracking precisa ser **fire-and-forget** sempre que apropriado.

Criar buffering/batching.

Exemplo conceitual:

usuário realiza várias ações
→ eventos entram em buffer local pequeno
→ envio em lote
→ endpoint Edge
→ validação
→ ingestão
→ processamento assíncrono

Utilizar mecanismos adequados disponíveis na arquitetura atual.

Avaliar:

* `navigator.sendBeacon`;
* `fetch(..., { keepalive: true })`;
* batching;
* Cloudflare Workers;
* mecanismos de fila disponíveis na infraestrutura;
* agregação server-side.

Não adicionar tecnologia simplesmente porque existe.

Primeiro analise quais recursos o projeto atual já utiliza e quais fazem sentido para Cloudflare + Supabase.

O tracking jamais pode travar:

* clique;
* navegação;
* carrinho;
* checkout;
* login.

Se o sistema de inteligência falhar, a loja deve continuar funcionando normalmente.

# 8. DECAY TEMPORAL

Interesses antigos devem perder força.

Implementar decaimento temporal.

Uma pessoa que viu Slides há 3 meses e hoje está navegando em outra categoria não pode continuar presa eternamente ao interesse anterior.

O decay deve favorecer:

* comportamento recente;
* intenção atual;
* sinais fortes.

Não recalcular todo o histórico a cada request.

Preferir atualização incremental.

# 47. RECENTEMENTE VISTOS

Criar “Vistos recentemente” de maneira leve.

Para visitante anônimo, pode usar armazenamento local apropriado quando possível.

Não precisa consultar servidor para cada item.

Quando autenticado, avaliar sincronização futura sem comprometer performance.

# 48. CARRINHO

* diversidade.

# 49. CHECKOUT

Checkout deve ser prioritariamente transacional.

Analytics no checkout deve ser mínimo, assíncrono e seguro.

# 50. OBSERVABILIDADE

Adicionar métricas técnicas.

# 51. BUDGETS DE PERFORMANCE

Defina e documente budgets.

* payload limitado;

Tracking:

* payload pequeno.

Home:

# 52. CORE WEB VITALS

Reservar espaço quando necessário.

# 53. LOAD TESTS

Criar testes de carga adequados aos recursos disponíveis no projeto.

Quero cenários como:

* 100 usuários simultâneos;
* 500;
* 1.000;
* vários milhares de requests concorrentes simulados quando possível.

Testar principalmente:

* endpoint de recomendação;
* ingestão de eventos;
* Home;
* ranking;
* busca relevante.

Não executar teste destrutivo contra produção.

Criar ambiente/configuração segura.

---

# 54. BENCHMARK

Antes e depois.

Registrar:

* latência;
* número de queries;
* payload;
* quantidade de writes;
* cache hit;
* consumo aproximado de recursos.

Não dizer “ficou mais rápido” sem medir.

---

# 55. EXPLAIN ANALYZE

Para queries importantes no Postgres, verificar plano de execução em ambiente seguro.

Detectar:

* sequential scans problemáticos;
* joins excessivos;
* sort caro;
* índices ausentes.

Não otimizar cegamente.

---

# 56. FALLBACK EM ALTA CARGA

Se o sistema detectar erro ou indisponibilidade:

não tentar fazer mais trabalho.

Degradar elegantemente para:

* cache;
* mais vendidos;
* ofertas;
* novidades;
* produtos estáticos elegíveis.

A loja deve sobreviver mesmo se o sistema inteligente estiver temporariamente offline.

---

# 57. CIRCUIT BREAKER / TIMEOUT

Não deixar o navegador esperando vários segundos por recomendação.

Usar timeout curto.

Se não responder:

fallback.

Inteligência é secundária.

Compra, produto e checkout são prioritários.

---

# 58. CUSTO

Quero máxima eficiência para aproveitar os planos atuais de Cloudflare e Supabase pelo maior tempo possível.

Evitar arquitetura que gere:

* milhões de requests inúteis;
* milhões de writes individuais;
* storage desnecessário;
* egress desnecessário;
* Functions chamadas para cada pequeno evento.

A escalabilidade precisa ser técnica **e financeiramente sustentável**.

---

# 59. PRIVACIDADE NO PAINEL

O painel “Inteligência da Loja” deve mostrar tendências agregadas.

Não criar uma tela invasiva do tipo:

“Pessoa X está olhando produto Y neste exato momento”

sem necessidade comercial/consentimento apropriado.

Priorizar analytics agregado.

---

# 60. TESTES FUNCIONAIS

Testar pelo menos:

Sem histórico.

### Visitante ativo

Vê diversos produtos.

### Interesse claro

Interage bastante com categoria específica.

Começa com Slides e passa para outra categoria.

Paginação correta.

### Produto sem estoque

### Nenhuma recomendação

Fallback funciona.

### Serviço de intelligence offline

Loja continua funcionando.
