Você está trabalhando no repositório do e-commerce **curti Z**.

## Objetivo

Faça uma auditoria e melhoria geral do sistema existente, priorizando **correção de bugs, segurança, desempenho, UX, SEO, consistência da marca e estabilidade**, SEM reconstruir o projeto e SEM alterar os produtos/dados de teste existentes.

O projeto já usa **Node.js 24**. Preserve essa versão como padrão oficial.

## REGRA CRÍTICA — NÃO MEXER NOS PRODUTOS

Os produtos atualmente cadastrados são produtos de teste e DEVEM permanecer exatamente como estão.

NÃO:

* alterar nomes de produtos;
* alterar descrições;
* alterar preços;
* alterar imagens;
* alterar estoque;
* alterar peso/dimensões;
* remover produtos;
* criar produtos apenas para teste;
* limpar banco;
* modificar seed de forma destrutiva.

Não tente "corrigir" dados de teste estranhos. Eles são intencionais.

# 1. Auditoria antes de editar

Antes das mudanças, entenda rapidamente a arquitetura existente.

Priorize somente arquivos relacionados às áreas que realmente precisam ser alteradas.

Não leia o repositório inteiro desnecessariamente.

Procure principalmente por:

* `apps/store`
* `apps/panel`
* APIs relacionadas ao catálogo
* autenticação/autorização
* Supabase/RLS
* componentes de imagens
* layouts
* `loading.tsx`
* metadata/manifest
* Cloudflare/OpenNext
* configurações Node/pnpm/Turbo
* documentação técnica relevante

Evite mudanças grandes sem necessidade.

Prefira **patches pequenos, reutilização de código existente e mínimo número de arquivos alterados**.

* preload somente quando realmente necessário;

* imagens de produto;

* layout shift;
* componentes client desnecessários;
* requests duplicadas;

* chamadas Supabase;
* APIs;

---

# 8. Loading profissional

Implemente um loading visual consistente.

Quero um **spinner circular girando no centro da página**, profissional, discreto e compatível com a identidade do curti Z.

Características:

* centralizado horizontal e verticalmente;
* animação suave;
* CSS puro;
* acessível;
* responsivo;
* sem biblioteca externa;
* sem causar layout shift;
* respeitar `prefers-reduced-motion`.

Use a arquitetura nativa do Next.js, incluindo `loading.tsx` onde fizer sentido.

Também utilize loading adequado em operações client-side que realmente aguardam dados ou ações.

Não deixe spinner infinito em caso de erro.

Evite bloquear toda a página para operações pequenas quando um loading local for melhor.

Crie um componente reutilizável se isso evitar duplicação.

Faça auditoria defensiva completa.

Verifique:

* autenticação;
* autorização;
* Supabase RLS;
* policies;
* service role;
* exposição de secrets;
* variáveis `NEXT_PUBLIC_*`;
* APIs;

* mass assignment;
* IDOR;
* acesso entre roles;
* endpoints administrativos;
* manipulação de preço pelo cliente;
* estoque;

Não exponha secrets.

Não enfraqueça RLS para fazer algo funcionar.
