Você está trabalhando no projeto **curti Z**.

Quero criar e padronizar páginas de erro profissionais para a Store, principalmente:

* 404;
* erro inesperado/500;
* recurso indisponível quando aplicável;
* estados de página inexistente ou conteúdo não encontrado.

Faça as alterações diretamente no código.

O objetivo não é apenas mostrar o erro.

Quero transformar essas páginas em uma oportunidade de:

1. explicar claramente o problema;
2. ajudar o usuário a continuar navegando;
3. recomendar produtos reais abaixo da mensagem;
4. manter a identidade visual do curti Z.

---

# 1. PRINCÍPIO PRINCIPAL

A página deve seguir esta ordem:

```text
ERRO

Título claro

Explicação curta

Ações para continuar

────────────────────────

Mensagem comercial discreta

Produtos recomendados
```

O erro deve vir primeiro.

As recomendações nunca devem parecer uma tentativa de esconder o problema.

---

# 2. DESIGN

Seguir o Design System atual da Store:

* fundo `#eeeeee` quando apropriado;
* superfícies claras;
* vermelho/bordô curti Z;
* tipografia limpa;
* bordas discretas;
* pouco ou nenhum uso de sombras;
* boa quantidade de espaço;
* responsivo;
* sem aparência genérica de template.

Não usar:

* desenhos infantis;
* emojis;
* animações exageradas;
* ilustrações genéricas de robôs;
* gradientes futuristas;
* glow;
* glassmorphism.

---

# 3. PÁGINA 404

Criar uma página 404 clara.

Exemplo conceitual:

```text
404

Não encontramos esta página.

O endereço pode ter mudado, estar incorreto ou não existir mais.

[ Voltar ao início ]   [ Continuar comprando ]
```

Pode incluir também:

```text
Buscar no curti Z
```

quando a busca já estiver disponível de forma reutilizável.

---

# 4. NÃO CULPAR O USUÁRIO

Evite mensagens como:

"Você digitou o endereço errado."

Prefira:

"O endereço pode ter mudado, estar incorreto ou não existir mais."

Tom:

* simples;
* humano;
* profissional.

---

# 5. SEÇÃO COMERCIAL ABAIXO

Depois da área principal do erro, adicionar uma separação visual discreta.

Exemplo:

```text
────────────────────────────

Enquanto isso, que tal continuar explorando?

Selecionamos alguns produtos que podem te interessar.
```

Ou uma frase curta equivalente mais natural.

Não usar linguagem agressiva de venda.

---

# 6. RECOMENDAÇÕES DE PRODUTO

Abaixo dessa mensagem, mostrar produtos reais.

Prioridade de seleção:

1. produtos mais vendidos;
2. lançamentos;
3. produtos em destaque;
4. produtos ativos com estoque;
5. fallback para produtos publicados disponíveis.

Se houver contexto de navegação anterior útil e seguro, pode priorizar categoria relacionada.

Não criar um sistema pesado de recomendação só para a página de erro.

Reutilize APIs e queries existentes.

---

# 7. REGRAS DAS RECOMENDAÇÕES

Não mostrar:

* produto inativo;
* produto não publicado;
* item duplicado;
* produto completamente indisponível quando houver alternativas.

Não inventar produtos.

Não alterar dados existentes.

---

# 8. QUANTIDADE

Desktop:

mostrar aproximadamente 4 produtos.

Mobile:

mostrar uma lista/carrossel horizontal compacto, usando `scroll-snap` se isso já combinar com os componentes atuais.

Não exagerar na quantidade.

A página continua sendo de erro.

---

# 9. CARDS

Reutilize o card de produto existente da Store.

Não criar um segundo Design System só para páginas de erro.

Mostrar:

* imagem;
* nome;
* preço;
* desconto real quando houver;
* favorito se fizer parte do card atual.

---

# 10. 500 / ERRO INESPERADO

Criar também uma experiência adequada para erros inesperados.

Exemplo:

```text
Algo não saiu como esperado.

Não foi possível carregar esta página agora.

[ Tentar novamente ]   [ Ir para o início ]
```

Abaixo:

se for seguro e a própria recomendação puder ser carregada independentemente, mostrar produtos.

IMPORTANTE:

Se o erro estiver relacionado ao backend/banco e as recomendações dependem do mesmo serviço que falhou, NÃO entrar em loop tentando buscar produtos.

Nesse caso, mostrar apenas caminhos seguros:

* Início
* Minha conta
* Ajuda

conforme aplicável.

---

# 11. NÃO EXPOR DETALHES TÉCNICOS

Nunca mostrar ao usuário:

* stack trace;
* SQL;
* Supabase error;
* nome de tabela;
* exception;
* token;
* request interno;
* caminho de arquivo;
* segredo;
* mensagem bruta do servidor.

Pode mostrar um código de suporte/request ID quando já existir infraestrutura segura para isso.

Exemplo:

```text
Código de referência: ABC123
```

somente se for realmente útil e já houver suporte no backend.

---

# 12. BOTÃO TENTAR NOVAMENTE

Em erros recuperáveis, oferecer:

**Tentar novamente**

Mas não criar loop automático.

A ação deve acontecer somente quando o usuário clicar.

---

# 13. NOT FOUND DO NEXT.JS

Use corretamente os mecanismos nativos do Next.js.

Revise e implemente quando necessário:

* `not-found.tsx`;
* `error.tsx`;
* `global-error.tsx`;

na estrutura apropriada da Store.

Não criar rotas improvisadas se o framework já fornece tratamento correto.

---

# 14. ERROS ESPECÍFICOS

Quando fizer sentido, trate também estados específicos como:

## Produto inexistente

```text
Produto não encontrado.
```

Abaixo:

```text
Veja outros produtos
```

e recomendações.

## Categoria inexistente

```text
Não encontramos esta categoria.
```

Abaixo:

categorias existentes ou produtos recomendados.

## Pedido inexistente ou inacessível

NÃO mostrar produtos automaticamente se isso prejudicar o contexto de conta/segurança.

Priorize:

* voltar para pedidos;
* atendimento.

Use julgamento por contexto.

---

# 15. SEGURANÇA

Nunca usar uma página de erro para confirmar existência de recurso protegido.

Exemplo:

pedido que pertence a outro usuário.

Não mostrar:

"Este pedido existe, mas você não tem acesso."

Prefira uma resposta neutra apropriada.

Evite enumeração de:

* pedidos;
* usuários;
* contas;
* chamados.

---

# 16. SEO DA 404

A 404 real deve continuar retornando status HTTP correto.

Não transformar uma página inexistente em `200 OK` apenas porque agora mostra produtos.

Isso é importante para SEO.

A experiência pode ser rica, mas o status continua sendo:

```text
404
```

quando realmente for uma página inexistente.

---

# 17. NÃO INDEXAR ERROS

Garanta que páginas de erro não sejam tratadas como páginas comerciais normais pelo SEO.

Não adicionar essas páginas ao sitemap.

---

# 18. PERFORMANCE

A mensagem de erro deve aparecer imediatamente.

Não bloquear a renderização aguardando recomendações.

Preferir:

```text
erro primeiro
↓
recomendações carregam depois
```

Se as recomendações demorarem, usar skeleton pequeno/localizado.

Não usar spinner de tela inteira.

---

# 19. FALLBACK DAS RECOMENDAÇÕES

Se a busca dos produtos falhar:

a página de erro continua funcional.

Não mostrar um segundo grande erro.

Simplesmente omitir a seção de recomendações ou mostrar um fallback leve.

A parte principal de recuperação deve continuar disponível.

---

# 20. MOBILE

Testar pelo menos:

* 320px;
* 375px;
* 390px;
* 430px.

No mobile:

* código do erro bem legível;
* título não gigante;
* botões fáceis de tocar;
* recomendações deslizam naturalmente;
* sem overflow;
* header/footer normais.

---

# 21. DESKTOP

Em desktop:

não deixar a mensagem perdida numa tela enorme.

Use largura máxima adequada e composição centralizada.

A seção de produtos pode utilizar mais largura abaixo.

Exemplo conceitual:

```text
              404
      Não encontramos esta página.

       [ Início ] [ Comprar ]

────────────────────────────────

Você pode gostar

[ produto ][ produto ][ produto ][ produto ]
```

---

# 22. TOM DE TEXTO

Use português brasileiro natural.

Evite textos como:

"Oops!"

"Algo deu ruim"

"Parece que você se perdeu no universo"

Quero linguagem profissional e simples.

---

# 23. NÃO USAR EMOJIS

Não adicionar emojis em nenhuma página de erro.

---

# 24. COMPONENTES REUTILIZÁVEIS

Se houver ganho real, criar componentes como:

```text
ErrorPageShell
ErrorActions
ErrorRecommendations
```

ou equivalentes compatíveis com o padrão atual.

Não criar abstrações demais.

---

# 25. ANALYTICS / OBSERVABILIDADE

Se já houver sistema de observabilidade:

registrar eventos de erro relevantes como:

* tipo de erro;
* rota;
* request ID;
* commit;
* ambiente.

Não registrar dados pessoais desnecessários.

Se já houver analytics comerciais, pode registrar visualização de 404 para descobrir links quebrados.

Não instalar ferramenta nova apenas para isso.

---

# 26. LINKS QUE GERAM 404

Durante a tarefa, procure rapidamente se existem links internos conhecidos apontando para páginas inexistentes.

Se encontrar:

corrigir esses links.

Não faça crawler enorme no repositório.

---

# 27. NÃO ALTERAR

Não alterar nesta tarefa:

* produtos;
* checkout;
* Mercado Pago;
* Melhor Envio;
* Resend;
* regras comerciais;
* painel interno;
* autenticação.

---

# 28. TESTES

Criar/ajustar testes para:

## 404

* rota inexistente;
* status correto;
* mensagem aparece;
* botão Início funciona;
* recomendações aparecem quando API está saudável.

## Erro de recomendação

* página principal continua utilizável;
* sem loop;
* sem segundo erro grande.

## Produto inexistente

* página adequada;
* recomendações reais.

## Mobile

* sem overflow;
* botões acessíveis;
* cards funcionam.

---

# 29. VALIDAÇÃO

Ao final execute:

```bash
pnpm lint
pnpm typecheck
pnpm test
```

e build/testes relevantes da Store.

Corrija regressões introduzidas.

---

# CRITÉRIO DE CONCLUSÃO

Só considere concluído quando:

* Store possuir 404 profissional;
* erros inesperados possuírem UX adequada;
* status HTTP correto for preservado;
* detalhes técnicos não vazarem;
* usuário tiver ações claras para continuar;
* produtos recomendados forem exibidos abaixo quando seguro;
* recomendação falhando não quebrar a página;
* mobile e desktop estiverem bem resolvidos;
* componentes seguirem o Design System curti Z;
* não houver emojis;
* testes passarem.
